## 2. Подтверждённые проблемы

Приоритеты: P1 — до публичного запуска голосования; P2 — стабилизация/корректность эксплуатации;
P3 — улучшение при измеренной необходимости. Критических P0 по доступному коду и проверкам не найдено.
Ни один локальный тест не доказывает безопасность уже работающего удалённого сайта.

### F1 — P1: недоверенный IP на Vercel — исправлено

**Место:** `src/lib/clientIp.ts:12–17`, исходный тест «заголовок Caddy главнее x-real-ip».
При `VERCEL=1` выражение сначала брало `X-Client-IP`, затем `x-real-ip`. Отправитель может задать
первый заголовок, меняя `ipHash` и обходя квоты. На VPS за показанным Caddy этот конкретный обход
не воспроизводится: Caddy перезаписывает свой заголовок, Node слушает localhost.

**Проверка:** три сценария (оба заголовка, только поддельный, пустой платформенный) сначала упали,
после выбора ровно одного заголовка по окружению проходят. Доверие платформенному заголовку
сверено с [Vercel Request Headers](https://vercel.com/docs/headers/request-headers#x-real-ip).
End-to-end проверка на реальном Vercel остаётся задачей оператора, изменения в кабинете не делались.

### F2 — P1: квота и запись не атомарны — исправлено этапом B

**Место:** `src/features/voting/service.ts:39–74`; `rateLimiting.ts:18–22`.
Несколько устройств параллельно читают одинаковые счётчики, все получают разрешение, затем
сохраняются. Уникальный индекс защищает пару match/deviceId, но не лимит разных устройств/IP.
**Воспроизведение:** `scripts/audit-db.ts`, 8 конкурентных вызовов настоящего сервиса с одним
ipHash и разными deviceId: **8 строк и 8 успешных ответов при лимите 5**. Шестой последовательный
голос блокируется. Аналогичная схема чтение→запись делает часовой лимит подверженным гонке;
отдельный параллельный тест границы 60 ещё нужен.

**Устранение:** условная вставка/upsert в одной атомарной операции SQLite либо согласованная
write-транзакция с повтором ожидаемых блокировок. Mutex в памяти не защищает разные Vercel instances.

### F3 — P1: повторный голос неправильно учитывает время и IP — исправлено этапом B

**Место:** `service.ts:45,53,56–57,85`; `rateLimiting.ts:20`.
Узнавание устройства ограничено текущим IP и 24 часами, а update меняет ipHash, сохраняя createdAt.
Обновление старого голоса с нового IP не попадает в свежий счётчик; обновление свежего голоса
переносит его учёт между IP. При заполненном часовом лимите старое известное устройство блокируется,
хотя в `slice-2-voting.md` повторный голос обещан как не нагружающий лимиты.

**Проверка:** настоящий голос с createdAt 2020 года обновлён с нового hash — свежий count=0;
тот же deviceId на IP с 60 свежими строками получает RATE_LIMITED. Это две проверенные ветки,
а не заявление, что любой update должен расходовать квоту. Нынешний комментарий `votesPerHour`
называет квоту **новых** голосов; предложено явно принять эту семантику и неизменяемый IP создания.
Если требуются лимиты всех запросов/всех активных устройств, одной таблицы последних оценок недостаточно:
нужен отдельный согласованный механизм учёта. Такой продуктовый выбор автоматически не сделан.

### F4 — P1: инструкция предлагала общие ресурсы Preview/Production — документация исправлена

**Место:** исходный `deploy/VERCEL.md`, § 2 п. 4; `package.json:8`; `payload.config.ts:37`.
Одна таблица значений «Production и Preview» направляла два окружения в одну БД. Preview build
запускает `payload migrate` до сборки; production initialization через prodMigrations тоже меняет схему.
Ошибка сборки или откат сайта не откатывает БД. Это подтверждённый дефект инструкции и опасный
путь исполнения, **не доказательство**, что пользователь уже выставил одинаковые токены.

**Устранение:** документация теперь требует отдельные БД/Blob/секреты; разделение build/migrate/runtime
предложено этапом C. Проверка CLI миграций и повторной инициализации выполнена локально; настройки
удалённых окружений требуют отдельной проверки без вывода секретов.

### F5 — P2: переполнение matchId даёт 500 — исправлено

**Место:** `src/features/voting/schema.ts:7`, `src/lib/queries/matches.ts`, числовые URL матча/OG.
Регулярное выражение разрешало строку из 400 цифр; Number превращал её в Infinity, драйвер падал.
**Проверка до:** HTTP POST `/api/vote` с 400 девятками вернул 500; лог — аргумент Infinity в SQL.
**Исправление:** API принимает только положительный safe integer; общий загрузчик панели отклоняет
некорректный number до обращения к БД. Регрессионный Vitest сначала красный, затем зелёный;
HTTP после исправления вернул 400 INVALID_INPUT, URL — 404 (см. результаты § 5).

### F6 — P2: обязательные связи мешают удалению — ожидает этап D

**Место:** `src/migrations/20260918_191820_initial.ts`, FK `votes.match_id`, `matches.event_id`,
`matches.athlete1_id`, `matches.athlete2_id`: одновременно NOT NULL и ON DELETE SET NULL.
Удаление родителя с зависимыми документами не может завершиться. На тестовой БД удаление матча
с голосами завершилось ошибкой. Это не рассинхронизация текущей схемы с миграциями: настройки совпадают.
**Устранение:** для MVP предпочтительно явно запрещать такое удаление с понятным сообщением и
указанием зависимостей. Cascade удалит оценки зрителей и без отдельного решения недопустим.

### F7 — P1/P2: эксплуатационные шаги не доведены до проверяемого запуска

**Место:** исходные `deploy/DEPLOY.md` § 3–5, `deploy/backup.sh:7–16`.
Публичный Caddy предлагалось включить до первого администратора. У Payload есть специальный
register-first-user, который при пустой users создаёт администратора через overrideAccess=true
(`node_modules/payload/dist/auth/operations/registerFirstUser.js:25–40`). Это штатный bootstrap,
но первый посетитель публичного пустого сайта может стать администратором. Инструкция теперь
требует закрытый bootstrap (P1); реальная пустота/доступность production не проверена.

Cron под armreview вызывал mkdir в `/var/backups`, не подготовив права каталога; tar предполагает
наличие media даже до первой загрузки. На стандартном новом VPS без этих каталогов бэкап не завершится.
Добавлены install -d с владельцем/правами и ручной первый запуск. Скрипт не проверен на Linux в этой
сессии. Внешняя копия, отчёт об ошибках и восстановление пока только инструкции (P1 перед запуском).
SQLite `.backup` хорош; обычное копирование живого файла с WAL предлагать вместо него нельзя.
БД и media не являются единым атомарным снимком; учтён период без редактирования изображений.
Blob вообще не покрывается VPS-скриптом. Секреты восстанавливаются из отдельного защищённого источника.

### F8 — P1 до запуска: контакты и утверждения политики не завершены

**Место:** `src/lib/siteConfig.ts:5–7`, `src/app/(frontend)/privacy/page.tsx`.
ФИО/почта — буквальные заглушки. Текст утверждает размещение в РФ и отсутствие передачи третьим
лицам, тогда как поддерживаемый альтернативный деплой использует внешние сервисы. Условие проблемы:
публикация с заглушками или выбор окружения, не соответствующего тексту. Настоящий хостинг неизвестен.
**Устранение:** владелец предоставляет контакты/оператора и утверждает текст под реальную схему.
Это проверка готовности контента, не юридическое заключение; старые суммы штрафов/цены в PROJECT
не проверялись и здесь не подтверждаются. Данные владельца не выдуманы и не подставлены.

## 4. Целевая архитектура и согласуемый переход

Подробная схема зависимостей и потоков — [STRUCTURE § 10](../../../STRUCTURE.md#10-целевая-архитектура-после-аудита-2026-09-21).
Сохраняем один Next/Payload монолит, чистую формулу, SQL-агрегаты, узкие props, уникальный индекс,
локальные изображения на VPS, SQLite и существующий Turso-вариант. Не нужны repository framework,
новая CMS, Redis, очереди, микросервисы, собственная админка или регистрация зрителей.

### A. Выполнено в рамках небольших исправлений

1. Выбор доверенного IP строго по окружению + регрессионные тесты F1.
2. Безопасный положительный integer ID на API-границе и перед запросом панели + тесты F5.

### B. Атомарная запись голоса (F2, F3) — договор принят 2026-09-22

Пользователь разрешил реализацию и приёмку всех B1–B6. Квоты действуют только на новые строки:
5 устройств на матч/IP за 24 часа, 60 голосов/IP за час. Повтор — `(match, deviceId)` без
фильтра возраста/IP; обновляются только четыре оценки и `updatedAt`, сохраняются `id`,
`createdAt`, исходный `ipHash`, `isHidden`. Остальные проверки допустимости обязательны.

Решение: один параметризованный `INSERT … SELECT … ON CONFLICT … DO UPDATE … RETURNING`
в `features/voting/writeVote.ts`; условие EXISTS для повтора либо обе свободные квоты.
Это исключает промежуток между чтением квоты и записью без новой таблицы/архитектурного слоя.
Лимиты берутся из `rateLimiting.ts`; окна строго `createdAt > now - window` (ровно на границе
строка уже не учитывается); скрытые голоса учитываются. Неожиданные ошибки — контролируемый 500.
Выбрана одна попытка statement, без прикладного retry; `busyTimeout: 1000` адаптера ограничивает
ожидание блокировки внутри SQLite. Это настройка соединения, запуск миграций не изменён.

Приёмка: реальные миграции на новой SQLite под TEMP, независимые соединения к одному файлу
для B1–B3; B4 — старый скрытый голос, новый IP и обе заполненные квоты; B5 — инъекция ошибки;
B6 — боты, no_contest и будущий турнир без записи. Дополнительно границы 1/24ч, разные IP,
сохранность служебных полей, npm test/lint/tsc/build, API и браузер.
Исходные F2/F3 воспроизводятся до изменения сервиса. Рабочая БД/Production не используются.
Без отдельной тестовой БД статус **«Turso не проверен»**; SQLite его не подтверждает.
Удаление матчей (D), запуск миграций (C), athleteStats и дизайн за границами B.
Новые индексы — только по доказанной необходимости отдельной миграцией.

**Схема и Payload:** реальные миграции подтвердили `id INTEGER PRIMARY KEY`, `match_id` с FK,
`match_deviceId_idx UNIQUE(match_id, device_id)`, текстовые даты ISO UTC с миллисекундами.
У Votes нет пользовательских hooks, versions или revalidation; остальные страницы динамические.
Публичный вход проверяет Zod (целые оценки 1–5, безопасный ID); сервис проверяет ботов, матч/окно.
SQL задаёт `is_hidden=0`, `created_at=updated_at=ctx.now` при вставке; при повторе меняет только
оценки/updatedAt. Публичные права коллекции и админское редактирование не менялись.
EXPLAIN использует существующие индексы пары, матча и IP; оснований добавлять индексы нет.

**Обоснование ожидания блокировки:** на установленном Windows libsql 0.4.7 вариант с нулевым
busy timeout и прикладным retry давал 8 успешных результатов при неполном сохранении строк.
Он отклонён. После `busyTimeout=1000` и удаления retry B1–B6 проходят; предел ожидания и 500
проверяются настоящей блокировкой отдельным соединением. Это не исследование всех режимов драйвера.
Атомарность statement опирается на [сериализацию записей SQLite](https://www.sqlite.org/isolation.html);
обновление только указанной пары — на [UPSERT](https://www.sqlite.org/lang_upsert.html).
