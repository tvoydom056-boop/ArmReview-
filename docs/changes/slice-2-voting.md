## Приём голоса (`features/voting/`)

Порядок в `castVote()` (`service.ts`): honeypot → «слишком быстро» → матч найден → `NOT_VOTABLE` → лимиты → `TOO_EARLY` → запись. Схема Zod проверяется раньше, в роуте `/api/vote`.

| # | WHEN | THEN | Проверка |
|---|---|---|---|
| 1 | оценка не целая или вне 1–5, `matchId` не число | `400 INVALID_INPUT`, записи нет | T `schema.test.ts` |
| 2 | honeypot `website` непустой | `200 OK`, голос не записан | T схема пропускает поле; **M** сам ответ (`service.ts:19`) |
| 3 | с `openedAt` до отправки меньше 3 с | `200 OK`, голос не записан | M (`service.ts:20`) |
| 4 | с одного `ipHash` за 24 ч на матче уже 5 устройств, приходит 6-е | `429 RATE_LIMITED` | T `rateLimiting.test.ts` |
| 5 | с одного `ipHash` за час уже 60 новых голосов | `429 RATE_LIMITED` | T `rateLimiting.test.ts` |
| 6 | дата турнира не наступила (до 00:00 МСК следующих суток) | `409 TOO_EARLY` | T `votingWindow.test.ts` |
| 6а | матч `no_contest` | `NOT_VOTABLE` | T `votingWindow.test.ts` |
| 7 | первый голос `deviceId` на матч | запись создана, `200 OK` | M |
| 8 | повторный голос того же `deviceId` | запись обновлена, новой нет, лимиты не нагружает | T лимиты; **M** обновление |
| 9 | два одновременных запроса с одним `deviceId` | одна запись, оба ответа успешны | M (`service.ts:71–86`) |
| 10 | голос сохранён | в `votes` только `ipHash`, сырого IP нет нигде, в т.ч. в логах | T хеш не содержит IP; **M** логи |
| 11 | анонимный `GET` к коллекции `votes` | данные не отдаются | M |

## Решения, принятые в коде

Пять вопросов, которые выявил разбор STRUCTURE.md, закрыты так:

| Вопрос | Решение | Где |
|---|---|---|
| Honeypot против схемы | схема принимает `website` любым, гасит `service` | `schema.ts:13` |
| Повторный голос и лимиты | известное устройство лимитом не блокируется; в 60/час считаются только новые голоса | `rateLimiting.ts:19–22` |
| Статус `RATE_LIMITED` | 429 | `app/api/vote/route.ts:14` |
| Момент открытия голосования | 00:00 МСК следующих суток, `TODO` к Владу | `votingWindow.ts` |
| Матчи с травмой / ДК / несостоявшиеся | голосовать можно, кроме `no_contest` (`TODO(вопрос 11)`) | `votingWindow.ts:24` |

## Что не закрыто

- Для service появился диагностический интеграционный скрипт аудита; проверки конкурентных лимитов
  выявили дефект, а не подтвердили готовность. После исправления нужен строгий регрессионный тест квот.
- STRUCTURE.md актуализирован аудитом (по-прежнему вне репозитория приложения).
- Вопросы к Владу 10 и 11 (PROJECT.md § 15) остаются с дефолтами.

## Проверено аудитом 2026-09-21

Команды, границы и полные результаты — [project-audit.md](project-audit.md#5-проверки-и-воспроизведение).
Новая временная SQLite, настоящие Payload/service и production HTTP; рабочая БД не использовалась.

| Сценарии | Факт |
|---|---|
| 1 | Vitest + HTTP malformed JSON и слишком большой ID; 400, не 500 |
| 2, 3 | DB script: ok без строки при honeypot/отправке раньше 3 секунд |
| 4 | Последовательное 6-е устройство отклонено; **8 параллельных дают 8 строк — дефект F2** |
| 5, 8 | Часовая квота срабатывает; **старый повторный голос при заполненной квоте отклоняется — F3** |
| 6, 6а | Дата — Vitest; no_contest — также настоящий service |
| 7–9 | Create/update сохраняют одну строку; 2 конкурентных вызова одного устройства — оба ok |
| 10 | Hash unit test, код записи содержит только ipHash; реальные инфраструктурные логи не проверены |
| 11 | Local API overrideAccess:false и HTTP GET votes/users →403; анонимная запись в коллекции →403 |
| 12–16 | Unit + SQL-рейтинг на настоящей БД: порог и пример 4.3 |
| 17 | isHidden исключает голос; повторная оценка не снимает скрытие |
| 18–20 | HTTP страницы и API работают; клики, модалка и обновление UI не проверены — браузер недоступен |

Новые проверки IP: Vercel игнорирует X-Client-IP и не использует его как fallback;
до исправления три регрессионных сценария падали. Это не тест реального ingress Vercel/Caddy.
